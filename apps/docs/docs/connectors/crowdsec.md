CrowdSec alerts and decisions from a Local API (LAPI): the scenario that fired, the source IP with its AS and country, and the ban or captcha decision taken. Machine login for full alerts, or a bouncer API key for decisions only. Read-only.

- **Connector id:** `crowdsec`
- **Category:** network

## Configuration

| Field | Label | Type | Required | Default | Notes |
|-------|-------|------|----------|---------|-------|
| `lapi_url` | LAPI URL | string | yes | — | Base URL of the CrowdSec Local API (default port 8080). |
| `machine_id` | Machine ID | string | no | — | From `cscli machines add`. Needed for alerts. |
| `password` | Machine password | secret | no | — | **encrypted at rest** |
| `api_key` | Bouncer API key | secret | no | — | **encrypted at rest** · From `cscli bouncers add`. Used for decisions only, and only when no machine is configured. |
| `verify_tls` | Verify TLS Certificate | boolean | no | `True` | — |

:::note Credential handling
`password`, `api_key` are encrypted at rest by the credential vault before the row is written, and decrypted only at poll time. The value is never logged and never returned by the API — a read of the saved connector shows the field as set, not its contents. See [credential vault](../operations/credentials.md).
:::

## Capabilities

- `pull_alerts`

## Setup

1. In the console, go to **Connectors → Add connector** and pick **CrowdSec**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

The connector talks to a CrowdSec **Local API** (LAPI), the same one your bouncers and agents use
(port 8080 by default). Run these on the host that runs CrowdSec; in Docker, prefix with
`docker exec crowdsec`.

**Alerts (recommended).** Create a machine for AiSOC:

```bash
cscli machines add aisoc --password '<a long random password>' --force-add
```

A machine added from the same host is auto-validated. If it was registered over the network, run
`cscli machines validate aisoc`. Enter `aisoc` as **Machine ID** and the password as **Machine password**.

**Decisions only (fallback).** Create a bouncer and enter its key as **Bouncer API key**:

```bash
cscli bouncers add aisoc
```

With only a key there are no scenarios, events or AS/country, just the active decisions. The first poll
returns every active decision; later polls return only new ones. A connectors-service restart replays
every active decision once. If both a machine and a key are set, the machine is used.

## What you get

| CrowdSec | AiSOC |
|----------|-------|
| `scenario` | title (`CrowdSec: <scenario>`), `rule_name` |
| `source.ip` (or `source.value` when scope is `Ip`) | `src_ip` |
| `source.cn`, `source.as_number`, `source.as_name` | `country`, `asn`, `as_name` |
| decision `type` and `duration` | `action`, `duration` |
| first event meta `target_fqdn`, `http_path` (or AppSec's `uri`), `http_status` | `target_host`, `http_path`, `http_status` (reverse-proxy logs such as the npmplus collection, and AppSec virtual patching) |
| the whole alert | `raw_event` |

Severity is `high` when a `ban` decision was taken, `medium` otherwise, and `low` for simulated alerts.
MITRE technique is set only where the scenario name makes it obvious: brute force (`brute`, `-bf`,
`stuffing`) is T1110, scans, probing, crawling and enumeration are T1595, and virtual patching
(`vpatch-*`) and CVE scenarios are T1190.

:::caution Limits
LAPI filters `since` on when an alert's bucket *started*, so the connector always looks back at least
one hour and drops repeats by alert id. `GET /v1/alerts` has no continuation, so a poll reads at most
500 alerts and logs `crowdsec.alerts_capped` if that binds.

LAPI records every community (CAPI) and subscribed-list blocklist pull as an alert
(`update : +15000/-0 IPs`, no source, thousands of `ban` decisions) and returns them by default. The
connector asks for `include_capi=false` and also drops any alert whose decisions all come from
`CAPI` or `lists`, so only detections on your own CrowdSec are raised. With a bouncer key the
decision stream is narrowed to `origins=crowdsec,cscli` for the same reason; without it the first
poll would raise every blocklisted IP.
:::

Read-only: nothing here adds or removes a decision.
